# 每月检查与季度反熵清单

> 由《附录 E：失败模式与反熵检查表》按当前目录和治理规则校准。出现信号不是失败，而是提醒你停止扩建、修复事实源和真实闭环；检查结果写入维护日志。

## 每月检查（约 30 分钟）

| 失败信号 | 立即动作 |
|---|---|
| 30 天只装修，没有决定或交付 | 冻结建设，只运行真实问题 |
| 说不清目录职责 | 回看各区 README，合并重复职责 |
| 判断回不到原文和时点 | 分离 Source 与 Knowledge，补来源 |
| AI 自动删除、发送或改权威内容 | 降为只读/草稿，检查版本差异 |
| 搜到很多却没有可引用证据 | 白名单 + 状态过滤 + 负向测试 |
| 从未做恢复演练 | 在临时副本完成一次恢复 |
| 连续两周维护超预算 | 删字段、停工具、缩短模板 |
| 字段很多但没人查询 | 删除无消费者字段 |
| 搜索指标好但行动没改善 | 停止调参，改看结果转化 |
| 一次情绪被写成长期偏好 | 降回 Candidate，等待跨场景证据 |

## 每季度反熵（约 1 小时）

- [ ] 列出从未触发或连续无产出的规则与定时任务
- [ ] 列出没有查询、审核或自动化消费者的字段
- [ ] 列出没有真实收益的插件、索引和工具
- [ ] 检查职责重复或长期无入口的目录
- [ ] 抽样回查最近 10 个重要回答能否找到来源
- [ ] 完成一次独立副本恢复演练
- [ ] 给每项做出保留、收缩、替换或停止决定

## 红队六问

1. 如果从零开始，我还会建同样的系统吗？
2. 长期没有进入真实任务的区域为什么存在？
3. 系统明天损坏，哪些核心资产仍无法恢复？
4. 新建内容时，哪些字段经常不知道怎么填？
5. 最近十次使用，有几次真正改变了行动或交付？
6. 系统在帮我工作，还是已经成为新的工作？

## 五条底线

- [ ] 每类事实只有一个默认 owner
- [ ] 重要结论可回到来源和时点
- [ ] 冲突、替代和过期不会被静默覆盖
- [ ] AI 写入受控，高风险操作可预览、可回滚
- [ ] 技术指标与真实价值分开验收

> 不强制删除固定比例。只删除有证据证明无消费者、无收益或职责重复的复杂度。
