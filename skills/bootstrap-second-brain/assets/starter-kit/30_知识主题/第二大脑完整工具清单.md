# 第二大脑完整工具清单

> 这不是“全部安装”的采购表，而是从基础能力到进阶能力的选型地图。产品能力、许可与价格会变化，使用前以官方说明为准。信息时点：2026-08-06。

## 0. 先看结论：推荐组合

本 Demo 推荐用四个组件建立第一版：

| 组件 | 角色 | 第一版怎么用 |
|---|---|---|
| **Markdown + 文件系统** | 事实核心 | 保存正文、元数据、原始附件和目录关系 |
| **Obsidian** | 人的工作台 | 编辑、导航、全文搜索、模板和链接 |
| **Git** | 变更审计与恢复 | 查看差异、保留历史、恢复误改 |
| **WorkBuddy** | AI 协作入口 | 读取指定上下文、生成草稿、修改文件、调用工具 |

### 初始化 Skill 工具分层

| 工具 | 分层 | 初始化语义 |
|---|---|---|
| **Python 3.11+** | `runtime-required` | 运行初始化 CLI 的前置条件；缺失时不调用 CLI，也不询问或写入 Vault 路径 |
| **Git** | `product-required` | create 的产品硬门禁；缺失或未验证时停止目标写入，不声明 initialized |
| **WorkBuddy** | `recommended` | 推荐 AI 协作入口；用户可以明确暂缓并记录影响 |
| **Obsidian** | `recommended` | 推荐人的工作台；用户可以明确暂缓并记录影响 |
| **社区插件** | `optional` | 默认不安装，只按反复出现的真实问题逐项选择和授权 |

第一版不需要社区插件、RAG、Memory OS 或复杂自动化。先用真实问题跑通“来源 → 知识 → 决策/项目 → 交付 → 结果”，再由重复出现的失败决定增加什么。

### 三条选型原则

1. **工具可替换，事实核心不能丢**：更换编辑器、Agent 或检索工具后，Markdown、附件和历史仍应可读、可导出、可恢复。
2. **先手工跑通，再自动化**：没有稳定输入、输出、失败信号和回滚方式，就不接定时任务。
3. **检索命中不等于可信答案**：搜索、语义召回和 AI 只返回候选，最终仍要检查来源、时点、状态和权限。

配套阅读：[[工具选择与升级门禁]]回答“什么时候才应该增加工具”。

## 1. 核心工具

| 工具 | 用途 | 推荐程度 | 获取方式 | 启用时机 |
|---|---|---|---|---|
| **Markdown** | 保存正文、元数据和关系 | 必需 | 编辑器内置支持 | 启动时 |
| **文件系统** | 保存 Markdown、附件和原始证据 | 必需 | 操作系统自带 | 启动时 |
| **Obsidian** | 编辑、导航、全文搜索、模板和双向链接 | 推荐工作台 | [官网](https://obsidian.md) | 启动时 |
| **Git** | 差异审查、历史追溯和误改恢复 | create 必需 | [官网](https://git-scm.com) | create 前 |
| **异地备份** | 应对设备损坏和本地副本丢失 | 强烈建议 | 私有仓库、加密云盘或离线介质 | 有不可替代内容时 |

Obsidian 不是事实核心，Git 也不等于备份。事实核心是可读取的正文和原件；Git 负责变化历史；异地备份负责本地失效后的恢复。

## 2. AI 协作工具：WorkBuddy

本 Demo 当前登记的 AI 协作入口为 WorkBuddy（recommended，可由其他文件型 Agent 替代）：

| 工具 | 形态 | 适合任务 | 获取方式 | 启用前核验 |
|---|---|---|---|---|
| **WorkBuddy** | 文件型 Agent | 跨文件任务、上下文读取、工具调用、交付回写 | [官网](https://www.workbuddy.ai/)；定时任务接入见 [[60_任务系统/20_WorkBuddy接入映射]] | 数据路径、模型提供方、权限范围、当前许可和日志位置 |

### 分三步开放权限

| 阶段 | 允许能力 | 验收后再升级 |
|---|---|---|
| **1. 读取与草稿** | 只读指定目录，在独立文件中生成建议 | 引用能回到原文，没有越权读取 |
| **2. 受限写入** | 只修改明确文件，展示 diff，保留恢复方式 | 多次修改范围准确，验证结果可复核 |
| **3. 工具调用** | 在白名单内执行搜索、检查、构建等工具 | 输入输出、超时、失败信号和停止条件明确 |

以下动作始终保留人工裁决：删除原件、改变事实 owner、修改权限、晋升 Candidate、对外发布或发送内容。

## 4. 社区插件：按问题添加

第一阶段先不安装社区插件。只有下表中的问题反复出现，再增加对应能力：

| 插件 | 解决的问题 | 启用信号 | 主要风险 |
|---|---|---|---|
| **Templater** | 动态日期、变量和条件模板 | 手工填充稳定成为负担 | 模板复杂化、脚本权限 |
| **Dataview** | 按状态、日期和字段查询 | 字段已经稳定并有固定查询 | 插件依赖、字段治理成本 |
| **Tasks** | 跨页面聚合任务 | 知识库确实需要统一任务视图 | 与正式任务系统形成双主 |
| **Kanban** | 轻量看板 | 存在稳定的可视化流转需求 | 重复建设项目管理系统 |
| **Calendar** | 时间导航 | 日记或周期记录成为主要入口 | 增加无消费者的视图 |
| **Excalidraw** | 白板与架构图 | 图形表达明显优于文本 | 专用格式和维护成本 |
| **Obsidian Git** | 自动执行 Git 操作 | 已手工跑通提交、冲突和恢复 | 误提交、冲突、提交噪声 |
| **Smart Connections** | 语义发现 | 同义表达持续漏召回 | 模型调用、索引范围、派生数据 |

安装前检查：插件会读取和修改哪些目录、是否联网、密钥放在哪里、索引能否删除重建、停用后会留下什么。装在本地不代表数据一定不会离开本机。

## 5. 检索能力：按阶梯升级

不要从 RAG 开始。每一级都应由上一级无法解决的真实问题触发：

| 级别 | 工具/方案 | 解决什么 | 升级信号 |
|---|---|---|---|
| **L0 导航** | 目录、索引页、文件名 | 已知位置和稳定入口 | 经常不知道应该去哪个目录 |
| **L1 全文搜索** | Obsidian Search、`grep` / `ripgrep` | 关键词和短语查找 | 准确关键词仍稳定漏召回 |
| **L2 结构化查询** | Properties、Dataview 或脚本 | 按状态、日期、类型筛选 | 手工筛选成为重复负担 |
| **L3 语义检索** | Smart Connections、本地 embedding | 同义表达与相似内容发现 | 有失败样本和前后对照评测 |
| **L4 对话式 RAG** | Khoj 或自建检索管线 | 多轮问答、过滤、引用和多端入口 | L3 已证明有收益，且能维护权限与索引 |

进阶实现还可以使用 SQLite FTS5 提升本地关键词检索性能。无论采用哪一级，结果都应返回原文路径、时点、状态和信任等级；索引、向量与缓存只是可删除重建的投影。

### 检索安全边界

- 不索引密钥、设备状态和无权进入当前上下文的内容；
- `rejected`、`superseded`、`archived` 与 Inbox 不进入默认回答作用域；
- 语义相似不代表事实一致，命中后仍需回查来源；
- 没有真实问题评测集，不宣称高级检索优于全文搜索。

## 6. 版本、同步与备份

三者解决不同问题：

| 能力 | 回答的问题 | 推荐实现 |
|---|---|---|
| **版本历史** | 改了什么，如何撤销误改 | Git 或具备可审查历史的工具 |
| **多端同步** | 多台设备如何获得接近的当前副本 | Obsidian Sync、系统云盘、Syncthing 或 WebDAV |
| **异地备份** | 本机和主副本同时损坏后如何恢复 | 私有仓库、加密云盘、离线加密介质 |

### 常见方案

| 方案 | 主要价值 | 适合场景 | 注意事项 |
|---|---|---|---|
| **Git + 私有仓库** | 差异、历史和异地副本 | 需要审计并能处理冲突 | 不是实时同步；私有不等于不会泄露 |
| **Obsidian Sync** | Obsidian 多端同步 | 重视原生多设备体验 | 许可、加密与版本能力以官方说明为准 |
| **iCloud / OneDrive 等** | 系统级文件同步 | 轻量多设备使用 | 冲突与历史能力因平台而异 |
| **Syncthing** | 点对点同步 | 愿意自行维护设备连接 | 在线状态、配置和冲突处理成本 |
| **WebDAV 服务** | 通用文件同步 | 已有可信 WebDAV 基础设施 | 服务许可、限额、加密与冲突处理 |
| **离线加密备份** | 独立灾难恢复副本 | 有不可替代资料 | 定期更新并真实测试恢复 |

至少做一次恢复演练：在临时位置恢复副本，确认 Markdown、附件、内部链接和历史可以使用。看到“已同步”不等于已经具备恢复能力。

## 7. 自动化与脚本

| 技术 | 用途 | 启用信号 | 前置条件 |
|---|---|---|---|
| **Python 3** | 检查、索引、批处理和 Memory OS | 手工流程稳定且成为瓶颈 | 明确输入、输出、权限和失败信号 |
| **Node.js** | 插件、转换和发布工具 | 现有工具无法满足稳定需求 | 能维护依赖和运行环境 |
| **Shell** | 文件检查、批量操作、定时任务 | 确定性步骤反复出现 | 小范围试跑、备份和安全参数 |
| **AppleScript** | macOS 跨应用自动化 | 系统级重复动作稳定 | 应用权限和可恢复性 |
| **PowerShell** | Windows 管理与自动化 | Windows 重复动作稳定 | 执行策略、权限和错误处理 |
| **系统定时器** | 提醒或只读巡检 | 手工节奏稳定运行后 | 日志、告警、停止条件和失败处理 |

自动化优先生成提醒或检查报告，不自动删除、合并、晋升知识或对外发送。运行方法见 [[99_维护记录/定时任务与知识进化]]，当前任务契约见 [[60_任务系统/00_任务注册表]]。

## 8. 方法体系：不是软件

| 方法 | 借鉴什么 | 不机械照搬什么 |
|---|---|---|
| **GTD** | 统一收件箱、清空开放回路、明确下一步 | 不让任务系统承担长期证据治理 |
| **PARA** | 用 Project / Area / Resource 表达行动关系 | 不用 PARA 取代事实所有权和来源分层 |
| **CODE** | Capture / Organize / Distill / Express 内容流 | 不把“表达过”视为已经可信 |
| **Zettelkasten** | 原子主张、显式链接、持续重组 | 不为链接数量拆碎所有笔记 |
| **记录管理** | 来源、时点、版本、审计和恢复 | 不把“有历史版本”误当“当前正确” |
| **DevOps / SRE** | 可观测、反馈、回滚、门禁和验收 | 不用运行指标替代真实任务结果 |

方法用于设计运行机制，工具用于降低执行成本。不要因为安装了插件，就认为对应方法已经落地。

## 9. 平台与成本提示

### 平台

- **macOS**：先运行 `git --version` 检查 Git 是否可用；Terminal 已提供基础 Shell，Homebrew 和第三方终端不是必需项。
- **Windows**：可使用 Git for Windows 和 PowerShell；Windows Terminal 和 WSL2 按真实工作流增加。
- **Linux**：通过发行版包管理器检查或安装 Git；Obsidian 安装方式以官方说明为准。
- **手机和平板**：适合搜索、阅读和轻量捕获；只有移动设备时，也可以先建立收件箱并记录三个真实问题。

### 成本

- Markdown、文件系统和部分编辑器可以零软件费用启动；
- WorkBuddy、同步、托管、模型调用或本地算力可能产生成本；
- 本清单不固化商业产品价格，使用前查看官方当前说明；
- 总拥有成本还包括学习、维护、冲突处理、备份和恢复演练时间。

## 10. 工具升级决策树

```text
开始：Markdown + 文件系统 + Obsidian + Git + WorkBuddy
  ↓
能否找到原文并恢复误改？
  否 → 先修目录、全文搜索、版本历史和备份
  是 → 继续
  ↓
是否出现反复、可复现的真实问题？
  否 → 保持当前组合，不增加插件
  是 → 记录失败样本
  ↓
问题属于哪一类？
  漏字段 → Templater
  批量筛选 → Dataview
  同义表达漏召回 → 语义检索
  多端访问 → 同步方案
  稳定重复步骤 → 自动化或 Skill
  ↓
新增工具是否可停用、可恢复、收益大于维护成本？
  否 → 回退
  是 → 保留并记录使用边界
```
